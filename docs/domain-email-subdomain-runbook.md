# AthletO domain, application subdomains, and Google Workspace runbook

This is an operator checklist, not an automation script. It intentionally keeps
DNS changes behind healthy origins and keeps domain, email, and application
credentials out of repositories and command history.

## Current state (observed 2026-08-25)

- `athleto.store` is already registered, delegated to Cloudflare, and serving
  the GitHub Pages marketing site over HTTPS. It does not need to be purchased.
- Squarespace is the registrar; Cloudflare is authoritative DNS. Once the
  Squarespace nameservers delegate to Cloudflare, records belong in Cloudflare,
  not in both dashboards.
- `app.athleto.store` currently resolves to an address that does not return a
  healthy HTTPS application.
- `user.athleto.store` and `api.athleto.store` currently have no public record.

Do not repair those names with placeholder IPs. Deploy and validate the two
origins first, then publish DNS.

## Desired routing

| Host | Origin | Public role |
| --- | --- | --- |
| `athleto.store` / `www` | GitHub Pages through Cloudflare | public marketing and formulation concepts |
| `app.athleto.store` | `athleto-web` ingress | canonical customer login, cart, wishlist, orders, gifts, checkout |
| `user.athleto.store` | same `athleto-web` ingress | compatibility alias; login may finish on canonical `app` host |
| `api.athleto.store` | `athleto-api` ingress | JSON API only; no browser session or marketing HTML |

The Kubernetes inputs live in the web/API repositories and are consumed by
`ORESoftware/k8s-cluster`. Replace their `:unreleased` image tags with immutable
digests during release.

## Application cutover order

1. Create the `athleto` namespace and operator-managed runtime secrets. Do not
   commit rendered Secrets, access tokens, database URLs, payment keys, or
   Shared Auth credentials.
2. Configure the AthletO Shared Auth application/realm, exact API audience and
   scopes, service introspection credential, and the exact callback
   `https://app.athleto.store/auth/callback`. Treat `user` as an alias or add a
   separately registered callback before allowing login there.
3. Deploy the API and confirm `/health/live`, then `/health/ready`, through the
   cluster service. Deploy the web service and repeat. The preview web service
   stays at one replica until sessions use a shared encrypted TTL store.
4. Issue/verify ingress certificates and test host routing before public DNS.
   Use the load balancer address with a local host override; verify the expected
   certificate, security headers, JSON content type, and readiness response.
5. Read the final load-balancer hostname or addresses from the cluster output.
   In Cloudflare, replace the stale `app` record and add `user` and `api` as
   explicit `CNAME`, `A`, or `AAAA` records pointing to that output. Cloudflare
   documents that `CNAME` points to a hostname and `A`/`AAAA` to IP addresses;
   do not invent a target. HTTP hostnames should normally be proxied once
   origin/TLS compatibility has been tested.
6. Set Cloudflare SSL/TLS to Full (strict), disable cache for authenticated app
   and API responses, preserve API request bodies and authorization headers,
   and rate-limit login, callback, checkout, promo, and gift-card write paths.
   Restrict the ingress/origin to Cloudflare or a private tunnel where the
   cluster design supports it.
7. Test from an external resolver and browser. Only then remove the previous
   `app` target. Keep a recorded rollback target and a short DNS TTL during the
   cutover window.

Cloudflare's current DNS guidance explains the available record types,
subdomain creation, and proxy behavior: [DNS record types](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/),
[create a subdomain](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-subdomain/),
and [manage DNS records](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-dns-records/).

## Google Workspace / Gmail setup

Use a dedicated Workspace super-admin account with MFA/passkeys and at least two
controlled recovery methods. Do not use a shared day-to-day mailbox as the only
super administrator.

1. Create the Workspace tenant for `athleto.store` and copy the domain
   verification TXT value generated by the Admin console. Add that exact TXT
   value at the Cloudflare apex and complete verification before changing mail.
2. Create the initial users and/or groups before MX cutover—for example
   `support@`, `orders@`, `security@`, and a monitored `dmarc@`. Decide which
   are licensed mailboxes, collaborative inboxes, or aliases rather than making
   every address an unmanaged forward.
3. For a new Workspace setup, add the current Google MX record at the apex:
   priority `1`, destination `smtp.google.com`. Remove conflicting non-Google MX
   records only after confirming they are not serving existing mail. Google's
   current help notes that older working Workspace tenants may retain the
   legacy `ASPMX` records; do not migrate a working tenant just for cosmetic
   consistency. Activate Gmail in the Admin console after the record is saved.
4. If Google Workspace is the only sender, publish one apex SPF TXT record:
   `v=spf1 include:_spf.google.com ~all`. If another platform sends as AthletO,
   merge it into the single SPF policy after inventorying it—never publish two
   separate SPF records.
5. After Gmail has been active long enough for the Admin console to offer a key,
   generate a 2048-bit DKIM key, publish the exact selector/TXT value Google
   provides (commonly `google._domainkey`), then click **Start authentication**
   and verify signed test mail. Do not paste a key from this document.
6. Wait until SPF and DKIM have been operating for at least 48 hours. Start
   DMARC in monitoring mode using a real, monitored aggregate-report mailbox,
   for example `v=DMARC1; p=none; rua=mailto:dmarc@athleto.store; adkim=s; aspf=s`.
   Review legitimate senders and reports for at least a week, then roll out
   `quarantine` to a small percentage, increase it, and finally consider
   `reject`. Do not jump to enforcement before every legitimate sender aligns.
7. Require MFA/passkeys, review OAuth app access, set retention and group posting
   rules, and document mailbox ownership and offboarding. Payment and order
   email should originate from a reviewed transactional sender whose SPF/DKIM
   alignment is included in the DMARC inventory—not from a developer laptop.

Google's current setup references are [MX records for Google Workspace](https://support.google.com/a/answer/87127),
[SPF](https://support.google.com/a/answer/33786),
[DKIM](https://support.google.com/a/answer/174124), and
[recommended DMARC rollout](https://support.google.com/a/answer/10032473).
Cloudflare's [email DNS guidance](https://developers.cloudflare.com/dns/manage-dns-records/how-to/email-records/)
also emphasizes that mail records are DNS-only; Cloudflare's HTTP proxy does
not proxy SMTP.

## Verification checklist

Run these checks from outside the cluster and from more than one resolver:

```sh
dig +short NS athleto.store
dig +short A app.athleto.store
dig +short A user.athleto.store
dig +short A api.athleto.store
dig +short MX athleto.store
dig +short TXT athleto.store
dig +short TXT google._domainkey.athleto.store
dig +short TXT _dmarc.athleto.store

curl --fail --show-error --silent https://app.athleto.store/health/ready
curl --fail --show-error --silent https://user.athleto.store/health/ready
curl --fail --show-error --silent https://api.athleto.store/health/ready
```

Also send authenticated test mail in both directions, inspect its headers for
SPF/DKIM/DMARC alignment, confirm the DMARC reporting mailbox receives reports,
exercise Shared Auth login/logout and CSRF failure, and create payment-provider
test-mode checkouts without declaring an order paid from the return URL.

## Rollback

- Application DNS: restore the recorded prior target or remove the new record;
  never point a login/API name to an origin that fails readiness.
- Gmail: retain the previous MX values until inbound and outbound tests pass,
  then remove them. If rollback is necessary, restore the complete previous MX
  set rather than mixing providers indefinitely.
- DMARC: move from enforcement back to `p=none` while diagnosing; do not remove
  SPF/DKIM or silence reports.
- Compromised credentials: revoke/rotate at the provider and secret manager,
  restart affected workloads, invalidate sessions, and audit access. Never
  “rotate” by committing a new secret to Git.
